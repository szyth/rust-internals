# login-cooldown-token

A hand-desugared state machine (`AuthenticateAndIssueToken`) for a conceptual `async fn authenticate_and_issue_token` that checks credentials fallibly (`verify_password(..)?`) before awaiting a login cooldown — no `async`/`await` syntax anywhere in the implementation.

`AuthenticateAndIssueToken` has three variants: `Start` (holds everything captured before the first suspension point), `WaitingOnCooldown` (suspended at the one `.await`, holding `username` and the in-flight `Cooldown`), and `Finished` (a sentinel, obtained for free from `std::mem::replace(&mut *self, ...::Finished)` at the top of `poll`, used to get owned access to the current variant's fields). `Start`'s arm runs `verify_password` first: on `Err`, it returns `Poll::Ready(Err(..))` immediately — no `println!`, no touching `cooldown` at all — matching `?`'s real desugaring as an immediate completion, never a suspension. On `Ok`, it prints once and transitions straight to `WaitingOnCooldown` without polling `cooldown` itself; `WaitingOnCooldown`'s arm is the single place that polls `Cooldown`, whether that's the very first poll (reached via fallthrough in the same `poll()` call) or a resumed one after a wake — deduplicating what would otherwise be identical polling logic in two variants. `Cooldown` itself is the same `Arc<AtomicBool>` + background-thread + `Waker` shape as `FlushSignal`. `block_on` is the same from-scratch, no-runtime executor pattern as other exercises (`ThreadWaker` + `std::task::Wake` + `thread::park`/`unpark`), extended to return `(T, poll_count)`.

Verified via two tests: `valid_credentials_resolve_after_cooldown_in_two_polls` (correct final `Ok(String)`, `println!` firing exactly once, exactly 2 polls — `Start`, then `WaitingOnCooldown` → `Ready`) and `invalid_credentials_short_circuit_in_one_poll_before_cooldown` (correct `Err(AuthError::InvalidCredentials)` in exactly **1** poll — proving the `?` failure never reaches `cooldown` at all, since if it had, the test would incur the real cooldown duration rather than resolving near-instantly).

A stretch step (adding a second, self-referential `.await` point — `SessionInfo::new(&username)` followed by `issue_token(&session).await`, mirroring the vault topic's own worked example) was attempted and deliberately abandoned once it hit the expected wall: giving the enum a lifetime parameter and a variant holding `username`, a `SessionInfo<'a>` borrowing it, and an `IssueToken<'a>` borrowing *that* produces real `E0597`/`E0505` errors — `username`/`session` don't live long enough, and can't be moved into the variant while still borrowed by a sibling field being constructed in the same value. That's exactly the self-referential-future problem topic 4.8 exists to solve via `Pin` projection; this exercise stops at the wall on purpose.
