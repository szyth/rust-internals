# ptr-box

A hand-rolled single-owner smart pointer over a raw pointer (`PtrBox<T>`), built to practice writing — and getting wrong — a correctly bounded `unsafe impl Send`/`Sync` for a type wrapping a raw pointer, plus a deliberately unsound sibling (`UnsoundPtrBox<T>`) that shows exactly what a missing bound costs.

`PtrBox<T>` holds `ptr: *mut T`, which is `!Send`/`!Sync` by default (structural auto-trait inference on the raw-pointer field). `new`/`get`/`Drop` give it `Box<T>`-like single ownership — not `Clone`, `Drop` frees the allocation exactly once. Its `unsafe impl<T: Send> Send for PtrBox<T> {}` and `unsafe impl<T: Sync> Sync for PtrBox<T> {}` are bounded on exactly what the type lets you do with `T`: transfer sole ownership (`Send`) and hand out `&T` via `get()` (`Sync`). Verified: `assert_send::<PtrBox<i32>>()`/`assert_sync::<PtrBox<i32>>()` pass; `assert_send::<PtrBox<Rc<i32>>>()` correctly fails to compile (`` the trait `Send` is not implemented for `Rc<i32>` ``, `PtrBox<Rc<i32>>` named as the reason); and a real `PtrBox<i32>` was moved into and dropped inside a spawned thread.

`UnsoundPtrBox<T>` is identical except its `unsafe impl<T> Send for UnsoundPtrBox<T> {}` carries **no bound on `T` at all** — it compiles for every `T`, including `Rc<i32>`, which is unconditionally `!Send`. Two live clones of the same `Rc<i32>`, each wrapped in its own `UnsoundPtrBox` and moved into its own thread, are each cloned again and dropped there — meaning two threads independently increment/decrement the same non-atomic `Cell<usize>` strong count with nothing synchronizing them. This compiles and runs, and completed cleanly across 20 consecutive runs with zero crashes — which is *not* evidence of soundness. The race window on a single `Cell<usize>` read-modify-write is narrow enough that ordinary thread scheduling essentially never lands two threads inside it by chance; the bug is real at the language's memory model regardless of whether any particular run happens to surface it. 

That's the whole point of this crate: "compiles and runs clean" is not "sound." `unsafe impl` is a promise made *to* the compiler that nothing checks it — `PtrBox`'s bound is an honest one, derived from what the type actually exposes; `UnsoundPtrBox`'s missing bound is exactly the kind of promise a reviewer should never accept without asking what's missing.
